# 路点停车后连接目标尾端被误判为阻挡车辆

## 根因与修复

新提供的机务段模板存档中，红色公司 5 号（车辆 ID 229）已使用任意车站、路签 18，认领了等待编组 505 的尾端车辆 637。原程序在 `TryPathReserveWithResultFlags` 中正确找到了预留轨道上的尾端，但 `IsCouplePartnerOf` 将目标的 Primary 与这个物理尾端指针直接比较，错误判定它是无关车辆，反复返回预留失败。此存档与前次的车站限定错误不同，原配置不需要调整。

修复仅在 `IsCouplePartnerOf` 将双方统一为 Primary 后验证有效的连接认领；包括铰接子单元、尾端车辆和 Primary 位于链中间的情况。未放宽路签、车站、速度或独占认领条件，真正的其他编组仍然阻挡预留。未修改自动待避决策、路点停车位置或原生预留清理规则，无新存档字段。

在完整资源的原始输入副本中，修复前 5 号持续预留失败；修复后第 460 个观察游戏刻完成连接并继续后续调度。输入副本及原文件摘要验证，原存档不改写。完整证据保存在 `D:/gpt/tools/depot-stop-followup-20261101`。

## 持续回归

- 单元场景 `Couple - reserved approach recognises a claimed rear vehicle`：合法目标尾端允许接近；无关编组仍阻挡，认领及随机状态不受影响。
- 真实行驶 `service_driving.py --modes recouple-waypoint`：正常解挂、驶向前方路点、停车、等待结束后向身后车厢寻路并重新连挂；行驶和读档均验证确实停过及完整恢复三节车厢。
- 原有路点停车／换向互斥、车次继承、装卸解挂、普通重新连挂继续验证。
- 按 AGENTS.md 执行自动待避核心、真实 NewGRF 设计速度、多出口及动态轨道行驶回归。详细数量和通过情况随 Windows 包的 `validation/acceptance.json` 提供。
- 本机服务器与两个客户端比较共享网络帧状态、车辆索引及错误报告；不据此宣称已验证跨平台或长期公共服务器负载。
